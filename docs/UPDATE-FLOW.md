# 🔄 اپدیت محصول موجود — طراحی

> قواعدِ کاربر در یک جمله: **«مثل محصول جدید عکس و کپشن و اطلاعات را بفرستم؛ پیش‌نمایش را با
> محصولِ انتخاب‌شده مقایسه کند و فقط چیزی را که فرق دارد عوض کند. چیزی که نفرستادم دست نخورد.
> قیمت ندادم ← قیمت قبلی. مدل تازه دادم ← مدل‌های قبلی جایش را به آن‌ها بدهند. موجودی عوض شد ←
> موجودیِ تازه.»** نوشتن مستقیم با REST است، بدون ZIP و بدون افزونه.

این سند «چرا و چطور» است؛ «چه چیزی را کاربر می‌بیند» در README (بخش اپدیت) و چک‌لیست دستی
(§۷) است.

## مسیر

```
🔄 اپدیت محصول ──► جست‌وجو (SKU/عنوان، مثل قبل) ──► انتخاب ──► [پیام راهنما]
    restock_flow.py                                   begin_update()
                                                          │
        عکس / کپشن / متن  ◄──────────────  همان سازندهٔ «محصول جدید» (product_flow.py)
                │            کارت زنده، undo، ویرایش فیلد، خطای گذرا، ...
                ▼
   Draft (ProductData) ──► update_plan.build(draft, محصولِ فروشگاه) ──► UpdatePlan ──► کارتِ تفاوت
                                                                          │
                                                       ✅ اعمال تغییرات   ▼
                                  محصول دوباره خوانده می‌شود، پلن دوباره ساخته می‌شود:
                                  signature فرق کرد؟ ← کارت دوباره، چیزی نوشته نمی‌شود
                                  وگرنه ← update_apply.apply(plan) ← تأیید از جوابِ فروشگاه
```

| لایه | فایل | مسئولیت |
|---|---|---|
| جست‌وجو و انتخاب | `bot/modules/restock_flow.py` | فقط پیدا کردن؛ هیچ ساخت/نوشتنی ندارد |
| سازنده | `bot/modules/product_flow.py` | همان ورودیِ محصول جدید؛ `mode="update"` + `session.target` |
| خواندنِ فروشگاه | `bot/services/product_match.py` | `find` و `read` (واریژن‌ها صفحه‌به‌صفحه؛ `variations_complete`) |
| **مقایسه** | `bot/services/update_plan.py` | تابعِ خالص: `build(product, draft) → UpdatePlan` (بدون شبکه) |
| **نوشتن** | `bot/services/update_apply.py` | تنها جایی که می‌نویسد؛ ترتیب، تأیید، شکست |
| کارت/تاریخچه | `keyboards/cards.py`, `products_ledger.py`, `product_journal.py` | `updated` / `update_failed` |

## قاعده‌ها (هر کدام یک گروه تست دارد)

| قاعده | رفتار | تست |
|---|---|---|
| **سکوت دستور نیست** | فیلدی که draft دربارهٔ آن ساکت است هیچ‌وقت لمس نمی‌شود؛ payload فقط فیلدهای عوض‌شده را دارد | `SilenceIsNotAnInstruction` |
| **برابر، تغییر نیست** | مقداری که فروشگاه همین را دارد در هیچ درخواستی نمی‌رود | `EqualIsNotAChange` |
| **فهرستِ مدل، کل فهرست است** | مدلِ فروشگاه که در فهرست نیست حذف؛ مدلِ تازه ساخته؛ مدلِ مشترک **همان واریژن** (شناسه حفظ) و فقط فیلدِ فرق‌دار نوشته می‌شود | `ModelsAreTheWholeList`, `WhatTheShopHoldsAfterwards` |
| **املای فروشگاه** | «iPhone 13 ProMax» با «iPhone 13 Pro Max» یکی است (`model_signature`)؛ املای خودِ فروشگاه می‌ماند | `test_the_same_model_in_another_spelling…` |
| **رنگ/ویژگی** | همان قاعدهٔ مدل؛ محوری که ذکر نشد گزینه‌هایش می‌ماند؛ رنگِ هر مدلِ مانده اگر رنگ نگفتی حفظ می‌شود | `test_models_that_stay_keep_the_colours…` |
| **عکس** | عکسِ تازه گالری را جایگزین می‌کند؛ از کتابخانهٔ رسانه چیزی پاک نمی‌شود | `test_photos_alone_are_an_update…` |
| **قیمتِ مدلِ تازه** | قیمتی که نوشته شد؛ وگرنه قیمتِ فعلیِ همان گروه (آیفون/اندروید) و به فروشنده گفته می‌شود؛ جایی نبود ← ⛔ | `NewVariations` |
| **عنوان** | فقط با `عنوان: …` یا ویرایش دستی. اولین خطِ توصیفی (حدسِ پارسر) عنوان نمی‌شود و کارت می‌گوید چه خوانده | `test_a_stray_line_is_never_taken…` |
| **SKU / دسته / توضیحات** | هیچ‌وقت؛ پیشوندِ SKU ناهماهنگ فقط هشدار است | `test_the_sku_is_never_rewritten…` |
| **پایه فروشگاه است** | همه‌چیز از `product_match.read` حساب می‌شود، نه از حافظهٔ ربات | `test_the_shops_own_view…` |
| **ناقص‌خوانده، برنامه نشود** | واریژن‌هایی که کامل خوانده نشدند (صفحهٔ دوم شکست) ← ⛔ و هیچ ساخت/حذفی | `RefusalsAreHonest`, `ReadingTheShop` |

## تطبیقِ واریژن‌ها

`shop_axes(product)` محورهای واریژن را از `attributes` (فیلد `variation=True`) می‌خواند (اگر هاست
`attributes` نفرستد، از خودِ واریژن‌ها). هر محور یک *kind* دارد (`model` / `color` / `other`) و
مقدارها با کلیدِ همان kind مقایسه می‌شوند (`model_signature`, `color_key`, `casefold`). محورهای
هدف = محورهای فروشگاه با گزینه‌های جایگزین‌شده؛ `build_combinations` (همان سازندهٔ محصول جدید) شبکهٔ
هدف را می‌دهد؛ هر ترکیب یا به یک واریژنِ موجود می‌خورد (به‌روزرسانی)، یا ندارد (ساخت)؛ واریژنِ
بی‌جفت حذف می‌شود.

دو احتیاط:

* اگر draft همان فهرست‌های فروشگاه را تکرار کند و شبکه دقیقاً محدود (مثلاً S24 فقط سبز) باشد، شبکه
  بازسازی **نمی‌شود** (واریژن‌هایی که فروشگاه عمداً ندارد ساخته نمی‌شود).
* اگر فروشگاه با خودش نخواند (واریژن روی مدلی که فهرست ندارد، یا مدلِ فهرست‌شده بی‌واریژن) و draft
  فهرست داده باشد، پلن «ساختار» حساب می‌شود و کار نیمه‌مانده را کامل می‌کند — همین است که «دوباره زدن»
  بعد از شکستِ نیمه‌کاره درست کار می‌کند.

## ترتیب نوشتن، تأیید، شکست

1. **آپلود عکس‌ها** — هنوز چیزی در محصول عوض نشده؛ شکستش هزینه‌ای ندارد.
2. **یک `PUT` برای خودِ محصول** (عنوان، گالری، فهرستِ کاملِ ویژگی‌ها، قیمت/موجودیِ محصول ساده). ویژگی‌ها را
   فروشگاه *جایگزین* می‌کند، پس هرچه عوض نمی‌شود همراه برمی‌گردد. ردِ والد همه‌چیز را متوقف می‌کند.
3. **`variations/batch`: ساخت + به‌روزرسانی** (صدتا‌صدتا؛ اگر هاست batch ندارد تک‌تک. batchی که *می‌سازد*
   با ۴۰۰ هرگز تک‌تک تکرار نمی‌شود: ممکن است بخشی ساخته شده باشد).
4. **`variations/batch`: حذف**، فقط اگر همهٔ ساخت/به‌روزرسانی‌ها تأیید شده باشند — محصولی که هم مدل‌های قدیمی را
   از دست داده و هم تازه‌ها را نساخته، از هر دو بدتر است.

هر ردیف از جوابِ خودِ فروشگاه تأیید می‌شود (`WRITTEN` = قیمت، قیمت ویژه، مدیریت موجودی، تعداد، وضعیت).
ردیفِ بلعیده‌شده تک‌تک نوشته می‌شود؛ echoِ ناهم‌خوان با *یک* خواندنِ مجدد سنجیده می‌شود؛ حذفِ بی‌echo هم همین‌طور.
چیزی که تأیید نشد «موفق» نیست (`unconfirmed`).

**سیگنیچر:** `UpdatePlan.signature()` هش همان چیزی است که *فرستاده می‌شود* (نه مقدارهای قدیمیِ کنارش)؛
موجودیِ فروشگاه با هر سفارش عوض می‌شود و «۵ → ۲۰» که «۴ → ۲۰» شد، همان تصمیم است.

**شکست = کارت باز می‌ماند.** نیمه‌کاره ← ledger `failed` (سبز نیست) + بنر «⚠️ بخشی اعمال شد: … دوباره بزن»؛
محصول دوباره خوانده می‌شود، پس کارت *باقی‌مانده* را نشان می‌دهد؛ دوباره زدن فقط همان را می‌فرستد. عکسی که یک‌بار
نشسته (`session.gallery_applied`) دوباره آپلود (و یتیم) نمی‌شود.

## قواعد UX که از «محصول جدید» ارث رسیده

یک پیام راهنما با «❌ لغو» که ویرایش نمی‌شود؛ کارتِ مرحله‌ای (قیمت/موجودی/عکس، بعد مدل‌ها)؛ هر پیامِ کاربر کارت
را پاک و تازه پایین چت می‌گذارد، تپ دکمه‌ها درجا ویرایش می‌کند؛ وضعیت = «typing…» نه پیام؛ خطا = toast روی دکمه /
⚡ روی پیام / یک خط روی همان کارت — هیچ‌وقت پیام تازه؛ کارتِ لاگ و ردپای HTTP فقط به **گروه لاگ**.
تأیید هم کارت را درجا به نتیجه تبدیل می‌کند.

## تصمیم‌هایی که گرفته شد (و کجا می‌شود عوضشان کرد)

* **فهرستِ مدل = جایگزینیِ کامل، با حفظِ واریژنِ مشترک.** «پاک و دوباره ساختنِ همه» همان وضعیتِ نهایی را
  می‌دهد ولی شناسهٔ واریژن‌ها (و هر چیزی که به آن‌ها وصل است) را از بین می‌برد؛ پس مدلِ مشترک می‌ماند و فقط
  فرق‌هایش نوشته می‌شود. (تغییر: `update_plan._plan_variable`.)
* **عنوان فقط صریح.** (تغییر: `product_flow._says_title`.)
* **محصولِ ساده → متغیر پشتیبانی نمی‌شود** (خطای شفاف). تبدیلِ نوع وسطِ نوشتنِ غیرتراکنشی ریسکِ محصولِ بی‌واریژن دارد.
* **ماتریس موجودی (طرح × مدل) در اپدیت رد می‌شود** (`E_STOCK_MATRIX_MODE`). موجودی را یک عدد بنویس.
* **عکسِ هم‌نامِ رنگ فقط روی واریژن‌های تازه** می‌نشیند.
* **ZIP دیگر ساخته نمی‌شود.** `_zip_manifest()` و افزونه سر جایشان‌اند (قرارداد)، ولی ربات صدایشان نمی‌زند.

## آزمایشش

```bash
.venv/bin/python scripts/simulate_update_flow.py            # پنج صحنهٔ کامل، هندلرهای واقعی، فروشگاه حافظه‌دار
.venv/bin/python -m unittest tests.test_update_plan tests.test_update_apply tests.test_update_flow tests.test_product_match
```

`tests/_update_shop.py` یک ووکامرسِ حافظه‌دار است (batch با ترتیب create → update → delete، سقف ۱۰۰، ردیفِ خطادار با
`error`، و دکمه‌های خرابی: route نبودن، ردیف بلعیده‌شده، echoی که نمی‌خواند…). «TISA_DRY_RUN=yes» + «دمو» همان مسیر را روی
فروشگاهِ آزمایشی می‌رود و `🧪 تست موفق؛ چیزی در سایت عوض نشد` می‌دهد.
