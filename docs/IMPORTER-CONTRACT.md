# قرارداد ربات ↔ افزونهٔ واردکنندهٔ وردپرس

> افزونهٔ WordPress داخل `tisa-product-importer.zip` است و **خارج از قلمرو این ریپو**
> (منبعش جای دیگری است و فایل داخل ریپو یک باینری ساخته‌شده — بند P2-7 سند
> `docs/CODE-REVIEW-AND-UPGRADE-PLAN.md`). برای همین اینجا فقط *قرارداد* نوشته می‌شود:
> ربات چه چیزی در `product.json` می‌گذارد و افزونه برای درست‌کارکردن به چه چیزی باید
> توجه کند. هیچ ویرایشی روی zip داخل این ریپو انجام نشده — چون فردا با یک build تازه
> از منبع، بی‌صدا از بین می‌رود.

> **به‌روزرسانی:** ربات دیگر ZIP نمی‌سازد — «🆕 محصول جدید» و «🔄 اپدیت محصول موجود» هر دو
> مستقیم با REST ووکامرس می‌نویسند (اپدیت: `bot/services/update_plan.py` +
> `update_apply.py`، شرحش در `docs/UPDATE-FLOW.md`). افزونه و این قرارداد سر جایشان‌اند،
> برای فایل‌هایی که دستی به افزونه داده می‌شود؛ `_zip_manifest()` در `product_flow.py`
> همان ساختاری را می‌سازد که تست‌ها قفلش کرده‌اند، ولی خودِ ربات صدایش نمی‌زند. جدول زیر
> دربارهٔ آن فایل است، نه رفتار فعلیِ ربات.

## چیزی که ربات (در آن فایل) می‌نوشت

`product.json` داخل ZIP (همان‌طور که `bot/modules/product_flow.py` می‌سازد):

| کلید | نمونه | معنا |
|---|---|---|
| `batch_id` | `"719e372625cf"` | شناسهٔ ۱۲تاییِ «این بسته». از محتوا + چت ساخته می‌شود (`bot/services/publish_batch.py`): همان متن، همان قیمت‌ها، همان عکس‌ها، همان چت ⇒ همان شناسه. نسخهٔ ربات ≥ ۰.۹.۰ |
| `mode` | `"new"` / `"update"` | شارژ/اپدیت از ساخت تازه جداست (در ربات فعلی هر دو REST‌اند) |
| `title`, `price`, `prices`, `sku_prefix`, `models`, `attributes`, `categories`, `model_colors`, `description`, `product_type`, `image_mode` | — | مثل قبل |
| `sale_price`, `stock`, `stock_status` | `498000`, `20`, `"outofstock"` | از نسخهٔ ۰.۱۱.۰: قیمت ویژهٔ تخفیف (هرگز جای `price` را نمی‌گیرد)، تعداد موجودی، و وضعیت موجودی با واژه‌های خود ووکامرس. **افزونهٔ فعلی این سه را نمی‌خواند** — یعنی محصول ZIPی بدون تخفیف/موجودی ساخته می‌شود، در حالی که مسیر REST هر دو را می‌نویسد. کلیدها با `??` بی‌ضررند و وقتی افزونه بخواندشان، همینجا آماده است |
| `stock_matrix` | `{ "پروانه": { "iPhone 13": 7, "iPhone 14": 0 } }` | جدول تعداد دقیقِ هر ترکیبِ طرح × مدل؛ مسیر REST آن را روی واریژن متناظر اعمال می‌کند. افزونهٔ فعلیِ ZIP هنوز این کلید را اعمال نمی‌کند |
| `model_prices` | `{ "iPhone 17 Pro": 598000 }` | از نسخهٔ ۰.۱۲.۰: قیمت اختصاصی هر مدل («قیمت سری ۱۷ ۵۹۸، بقیه ۴۹۸»). مسیر REST آن را روی واریژن همان مدل می‌نویسد؛ افزونهٔ فعلی این کلید را نمی‌خواند (اعتبارسنجیِ ربات دیگر آن را برای اپدیت رد نمی‌کند، چون اپدیت با REST می‌نویسد) |
| `wholesale_price`, `wholesale_model_prices` | `448000`, `{ "iPhone 17 Pro": 448000 }` | قیمت همکاری/عمده. فقط ثبت و نمایش داده می‌شود؛ نه قیمت ویژه است و نه جای `price`/`model_prices` را می‌گیرد، و **در هیچ مسیری روی سایت اعمال نمی‌شود** |

**این اختلاف عددی است، نه حدس:** `bot/services/importer_contract.py` نسخه را از هدرِ
خودِ `tisa-product-importer.php` (داخل zip کنار ریپو) می‌خواند و اگر زیر
`MIN_VERSION_FOR_PRICE_FIELDS = (0, 8)` باشد، همان را در «📊 وضعیت»، «🩺 عیب‌یابی» و
`python main.py --check-config` می‌نویسد. پس اگر افزونه را تازه کردی و آن سه کلید را
خواند، عددِ هدر را عوض کن — این جدول باید همان را بگوید؛ اگر روزی افزونه هیچ‌وقت
نخواندشان، سطرِ بالا جای گفتنِ آن است، نه یک فیلدِ بی‌مصرفِ تازه در بسته.

همین `batch_id` در مسیر REST هم به‌عنوان متای محصول نوشته می‌شود:

- `tisa_batch_id` → همان شناسه (کلید مقایسه)
- `tisa_source` → JSON با `chat_id`, `thread_id`, `images`, `variations`, `bot_version`, `captured_at`

## کاری که افزونه باید بکند (قطعهٔ آماده)

هدف: آپلود دوبارهٔ **همان فایل** (یا فایلِ یک تلاش نیمه‌کارهٔ دیگر) محصول دومی نسازد.

داخل `import()`، بعد از اینکه `product.json` decoded شد و بررسی‌های `title/price/prefix/models`
رد شد، و **قبل از** `self::next_sku($prefix)`:

```php
// ♻️ idempotency: a package we already imported must not become a second product.
$batch = sanitize_text_field((string)($data['batch_id'] ?? ''));
if ($batch !== '') {
    $done = get_posts([
        'post_type' => 'product', 'post_status' => 'any', 'numberposts' => 1,
        'meta_key' => '_tisa_batch_id', 'meta_value' => $batch, 'fields' => 'ids',
    ]);
    if ($done) {
        self::remove_dir($dir);
        self::success('این بسته پیش‌تر وارد شده بود؛ محصول دومی ساخته نشد.', (int) $done[0]);
    }
}
```

و داخل بلوک ساخت محصول، کنار `update_post_meta($product_id, '_sku', $sku);`:

```php
if ($batch !== '') update_post_meta($product_id, '_tisa_batch_id', $batch);
```

هر دو تکه عقب‌نگر‌اند: ZIP های قدیمی که `batch_id` ندارند دقیقاً مثل قبل رفتار می‌کنند
(`$batch === ''` ⇒ هیچ جستجویی انجام نمی‌شود، هیچ متایی نوشته نمی‌شود).

## چیزی که افزونه *ندارد* و رباتِ REST هم عمداً اضافه نمی‌کند

- **SKU روی واریژن.** طرح اولیه (§4.4) قول `BO148-17PMX-WHT` را داده بود؛ خود افزونه
  صریحاً می‌نویسد «SKU جداگانه برای variationها ساخته نمی‌شود». افزودنش فقط در مسیر
  REST یعنی یک محتوا، دو فروشگاهِ متفاوت — و «دو فروشگاه» دقیقاً همان چیزی است که کل
  این فاز داشت می‌بندد. پس هیچ‌کدام از دو مسیر SKU واریژن نمی‌نویسد.
- **تصویر هر رنگ.** در مسیر REST، اگر نام فایل هم‌نام رنگ باشد (`01_مشکی.jpg`) به همان
  واریژن می‌چسبد. در ZIP این کار عمداً انجام نمی‌شود: `attach_images()` فایل‌ها را به‌ترتیب
  به گالری می‌زند و هیچ نقشی برای واریژن نمی‌شناسد، پس هر «سازگاری» یک‌طرفه فقط فرق
  دو مسیر را عمیق‌تر می‌کرد. اگر روزی افزونه نقش رنگ را پذیرفت، نام فایل‌ها در
  `images/` همان است که ربات دیده — چیزی برای تغییر نمی‌ماند.
- `status: inherit` روی واریژن: نه اینجا، نه در افزونه، نه در `create_all_variations`
  خود ووکامرس. والد `draft` است و ارث بردنِ آن یعنی واریژن نامرئی در فروشگاهِ زنده؛
  هر دو مسیر `publish` می‌نویسند (منتشرِ نهایی همان‌طور که هست از والد کنترل می‌شود).

## بلوک‌های محتوا (`blocks`) — عمداً در فایل نیست

فاز ۲ «قرارداد هم‌راستا با بلوک‌ها» را به فاز ۶ موکول کرد؛ نتیجه‌اش این بند است، نه یک کلید تازه:

* ربات **همین حالا** `blocks` را در `product.json` نمی‌نویسد. ساختار تایپ‌شدهٔ پست
  (`Block` با `roles` و `line_no`/`message` در `bot/services/postmodel.py`) فقط در مسیر
  استخراج و پیش‌نمایش مصرف می‌شود. نوشتن کلیدی که هیچ نسخه‌ای از افزونه نمی‌خواند،
  همان کاری بود که `sale_price`/`stock` کرد و شد منبع سوءتفاهم.
* اگر روزی لازم شد (توضیحِ ساختاریافته، بلوک سئو، …) قرارداد این شکل است:
  `"blocks": [{"role": "price|model|color|meta|prose", "line_no": 3, "message_id": 41,
  "text": "…"}]` — همان چیزی که فروشنده نوشته، به همان ترتیبِ خط‌ها، بدون عددِ تبدیل‌شده.
  افزونه باید آن را بلوک‌به‌بلوک در `post_content` بگذارد و اگر `blocks` نبود به
  `description` برگردد. این فایل قرارداد است، نه الزام: نسخه‌ای از افزونه که `blocks`
  را نمی‌شناسد باید همچنان بتواند `product.json` را کامل بخواند.
* تا آن روز، هر مقداری که در فایل نیست یعنی ربات هم ارسالش نکرده است — پس جوابِ
  «چرا در وردپرس نیست؟» همین‌جا نوشته شده، نه در لاگ.

## نکته‌ها

- اگر محصولِ نیمه‌کاره از تلاش قبلی پیدا شد، افزونه می‌تواند به‌جای «ساخت دوباره»،
  همان `product_id` را نشان بدهد و به کاربر بگوید «ادامه بده» — این را ربات در مسیر
  REST انجام می‌دهد (واریژن‌های جاافتاده را اضافه می‌کند)؛ برای ZIP فعلاً همین
  «وارد نشد، همین است» کافی و امن‌تر است.
- `_tisa_batch_id` (با underscore) متای داخلی WordPress است؛ `tisa_batch_id` همان چیز روی
  محصول ووکامرس از مسیر REST. دو اسم، دو مسیر، یک مقدار.
- ربات **هیچ‌وقت** ZIP را پاک نمی‌کند و چیزی روی سایت با ZIP کار نمی‌کند؛ پس اگر افزونه
  این تکه را نگذارد، فقط تشخیص تکراری در مسیر افزونه از دست می‌رود — مسیر REST سالم می‌ماند.
