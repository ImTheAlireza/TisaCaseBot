# 🔧 ران‌بوک عملیات — TisaPostToWP

این سند راهنمای نصب نیست (آن `README.md` است). این‌جا فقط کارهایی هست که
**روی سرور، بعد از نصب** انجام می‌شود: ری‌استارت، بکاپ، دیسک پر، SKU mahtو‌خورده،
افزودن برند، و «چیزی منتشر نشد، حالا چی؟».

> دو قانون که همه‌جا تکرار می‌شوند، چون هر دو را یک‌بار نقض کردیم:
> 1. **همیشه قبل از هر کاری `python main.py --check-config`** — هیچ درخواست شبکه‌ای
>    نمی‌زند و همهٔ چیزهای محلی را می‌گوید (کلیدها، دیسک، صف، دفترها، افزونهٔ ZIP).
> 2. **هرگز دو پروسه با یک `BOT_TOKEN`.** supervisor و systemd و docker با هم = درخواست‌ها
>    بین پروسه‌ها تقسیم می‌شود و یک جریان نیمه‌کاره در یکی و جوابش در دیگری می‌ماند.

## ۱) ری‌استارت و استقرار

### با supervisor (همان که ربات با دکمهٔ «🔄 ری‌استارت» انجام می‌دهد)

```bash
supervisorctl status tisabot          # نامِ برنامه از SUPERVISOR_PROGRAM در .env
supervisorctl restart tisabot
tail -n 40 logs/bot.log
```

اگر `supervisorctl` به supervisord نرسد («refused connection»), ربات خودش با
`-c /etc/supervisor/supervisord.conf` و سوکت‌های معمول امتحان می‌کند؛ اگر باز نشد،
`SUPERVISOR_CONF` یا `SUPERVISOR_URL` را در `.env` صریح بگذار.

### با systemd (واحد آماده: `deploy/tisaposttowp.service`)

```bash
sudo systemctl restart tisaposttowp
journalctl -u tisaposttowp -n 50 --no-pager
```

در این حالت دکمهٔ «🔄 ری‌استارت» داخل ربات کار **نمی‌کند** و «📊 وضعیت» هم همین را
می‌گوید (`supervisorctl` روی PATH نیست) — عمدی است: ری‌استارتِ سرویس را رباتِ درونِ
سرویس نباید انجام بدهد.

### با Docker

```bash
docker build -t tisaposttowp .
docker run -d --name tisaposttowp --restart unless-stopped \
  --env-file /etc/tisaposttowp.env \
  -v tisaposttowp-data:/var/lib/tisaposttowp \
  tisaposttowp
docker logs --tail 50 tisaposttowp
```

داده‌ها در volume هستند؛ `docker rm` آن‌ها را نمی‌پَراند. `healthcheck` ایمیج همان
`--check-config` است، پس با `.env` ناقص کانتینر «سالمِ قرمز» بالا نمی‌آید.

### استقرار نسخهٔ جدید

```bash
cd /opt/tisaposttowp
git fetch --all && git status --short          # چیزی محلی عوض کرده‌ای؟
python main.py --check-config                  # پیش از کشیدن هم ببین چه چیزی هست
git pull --ff-only
pip install -r requirements.txt                # هرگز بدون این مراحل را «تمام» نکن
python main.py --check-config                  # بعدش دوباره: وابستگی تازه = کلید تازه
supervisorctl restart tisabot                  # یا systemctl restart tisaposttowp
```

**چطور بفهمم واقعاً بالا آمده؟** دو نشانهٔ واقعی هست، نه حدس:

* پیامِ استارت در `logs/bot.log` (و اگر `LOG_CHAT_ID` تنظیم باشد، یادداشتِ
  «♻️ ربات با موفقیت ری‌استارت شد» روی همان پیامِ ری‌استارت ویرایش می‌شود);
* اگر جریان نیمه‌کاری از قبل مانده باشد، ربات در اولین فرصت **صادقانه** می‌گوید چندتا بوده
  (`data/flow_state.json`) — این را جدی بگیر: یعنی آخرین بار وسط کار کشته شده است.

## ۲) دیسک، لاگ‌ها و فایل‌های موقت

```bash
df -h .                                                   # «📊 وضعیت» همین را خوانده می‌کند
du -sh logs data /tmp/tisaposttowp-* 2>/dev/null
```

* `logs/bot.log` چرخشی است (`bot/utils/logging.py`); اگر حجمش
  اذیتت کرد، `LOG_LEVEL=WARNING` موقتاً جواب می‌دهد — ولی شکستنِ انتشار را هم کم‌صدا
  نمی‌کند، فقط بقیه را ساکت می‌کند.
* `/tmp/tisaposttowp-*` و `/tmp/tisaposttowp-tracking-*` پوشه‌های موقت جریان‌ها هستند.
  یک جاروی ساعتی فایل‌های قدیمی‌تر از `TEMP_TTL_HOURS` (پیش‌فرض ۱۲ ساعت) را پاک می‌کند؛
  پاک‌کردن دستیِ **همین الان** فقط وقتی امن است که جریانی باز نباشد (رباط در آن لحظه
  عکسش را از همان‌جا آپلود می‌کند).
* `data/outbox_files/` کپیِ عکس‌هایِ در صف است. وقتی صف خالی است، پوشه باید خالی باشد؛
  اگر پُر مانده، یعنی چیزی بین queue و تخلیه ری‌استارت شده — با `--check-config`
  تعدادِ صف را ببین، بعد پاک کن.

## ۳) SKU شبح (ghost SKU)

علامت‌ها: در لاگ «SKU collision»، یا محصولی که روی سایت هست ولی ربات دوباره شماره‌اش را
می‌دهد. دلیلش یکی از این سه است: محصولی **خارج از ربات** با همان SKU ساخته شده، یک
محصول trash/draft شمارش نشده، یا `data/sku_state.json` عددِ پایین‌تری را یادش مانده.

**۱. روی سایت نگاه کن چه کسی آن SKU را گرفته** (MariaDB/MySQL دیتابیس وردپرس):

```sql
SELECT p.ID, p.post_title, p.post_status, m.meta_value AS sku
FROM wp_posts p
JOIN wp_postmeta m ON m.post_id = p.ID
WHERE m.meta_key = '_sku' AND m.meta_value LIKE 'TISA%'
ORDER BY p.ID DESC
LIMIT 30;
```

`post_status` را ببین: ربات موقعِ **اسکنِ کاتالوگ** همان فیلترهای `wc/v3` را می‌خواند که
`trash` و `auto-draft` را نمی‌بینند؛ پس یک SKU در trash برای ربات «آزاد» است و ووکامرس
گاهی همان را گرفته می‌داند. اگر خواستی، با همین کوئری پیدایش کن و `DELETE` یا تغییر SKU
بده — **از طریقِ خودِ wp-admin، نه با نوشتن مستقیم در جدول** (ووکامرس سه جدول را با هم
به‌روز می‌کند).

**۲. حافظهٔ خود ربات** در `data/sku_state.json` است:

```bash
cat data/sku_state.json          # {"version":1,"prefixes":{"TISA":{"max":1042,"ts":...}}}
rm data/sku_state.json           # یا صبر کن: هر ۶۰۰ ثانیه خودش بی‌اعتبار می‌شود
```

`rm` بدون ری‌استارت هم کافی است (فایل هر بار از دیسک خوانده می‌شود)؛ ربات شمارهٔ بعدی را از
اسکنِ کاتالوگ شروع می‌کند و اگر افزونهٔ شمارندهٔ SKU نصب باشد، از همان می‌پرسد.

**۳. اگر افزونهٔ SKU نصب است** و مسیرش جواب نمی‌دهد، «🩺 عیب‌یابی» می‌گوید
`افزونهٔ SKU — نصب نیست (HTTP 404)`؛ ربات در همان حالت به اسکنِ کاتالوگ برمی‌گردد، پس
هیچ انتشاری متوقف نمی‌شود. مسیرِ REST را که در `bot/services/sku.py` (`PLUGIN_ROUTE`)
است، عوض نکن مگر اینکه افزونه را هم عوض کرده باشی — عیب‌یابی همان یک ثابت را می‌خواند.

## ۴) افزودن یک برند به کاتالوگ

کاتالوگِ پیش‌فرض در `bot/services/model_catalog.py` است؛ **ویرایشِ محلیِ تو** در
`data/model_catalog.json` (فایلِ ترک‌شده نیست، پس با deploy نمی‌پرد):

```bash
cat > data/model_catalog.json <<'JSON'
{
  "brands": {
    "nothing": {
      "label": "Nothing",
      "words": ["nothing", "ناتینگ"],
      "variants": ["phone (2a)", "phone 2a", "phone 1"],
      "forbidden_variants": ["pro max"]
    }
  }
}
JSON
```

* `words`: املاهایی که در پیام فروشنده می‌آید (فارسی و لاتین) — روی همین‌ها casefold
  تطبیق داده می‌شود.
* `variants`: پسوندهایی که برای آن برند **وجود دارند**؛ `forbidden_variants` آن‌هایی که
  وجود ندارند و ربات به‌جای ساختنِ مدل، هشدار می‌دهد.
* بعد از ویرایش، ربات را ری‌استارت کن (کشِ `_catalog()` در حافظهٔ پروسه است).

تستِ سریع: «🔍 تست پارسر» را با همان متن واقعی بزن؛ اگر برندی ناشناخته بماند، ربات
پیشنهادِ فاصلهٔ ویرایشی می‌دهد و تأییدت را در `data/vocabulary.json` ذخیره می‌کند —
یعنی لازم نیست هر بار فایل را ویرایش کنی.

## ۵) چیزی منتشر نشد

اول «📊 وضعیت» (آفلاین، فوری)، بعد اگر لازم شد «🩺 عیب‌یابی» (همهٔ بررسی‌های زنده،
هم‌زمان). هر خط کارت یک ↳ دارد؛ از همان شروع کن. ترتیبِ تصمیم:

1. **🔴 WooCommerce پاسخ نمی‌دهد** → از همان ماشین تست بزن:
   ```bash
   curl -sS -o /dev/null -w '%{http_code}\n' \
     "https://shop.example/wp-json/wc/v3/products?per_page=1&consumer_key=CK&consumer_secret=CS"
   ```
   `200` ولی ربات قرمز می‌گوید → کلیدها در `.env` عوض شده‌اند؛ `401/403` → permissions
   کلید؛ `000` → DNS/فایروال.
1b. **«فروشگاه به هیچ درخواستی پاسخ نداد» / «اتصال برقرار نشد»** → این خطا **پیش‌آزمونِ
   ایمنی** است: اولین درخواستِ هر انتشار `GET /wp-json/wc/v3/tisa-health` است و تا جواب
   ندهد، هیچ عکسی آپلود و هیچ محصولی ساخته نمی‌شود (یعنی نیم‌ساخته‌ای وجود ندارد و
   صف، همان بسته را از اول تلاش می‌کند).
   **ترمینال لازم نداری:** «🛰 شبکهٔ سایت (بدون ترمینال)» در «🏓 تست‌های تک‌تک» همان
   چهار سؤال را از *خودِ سرورِ ربات* می‌پرسد — صفحهٔ اصلی، REST بدون کلید،
   `tisa-health` بدون کلید و `tisa-health` با کلید — و می‌گوید کدام طبقه خراب است
   (هاست / فایروال / افزونه / کلید). همه‌اش GET است، پس وسطِ قطعی هم زدنش بی‌خطر است
   و در dry-run هم اجرا می‌شود. همان «🩺 عیب‌یابی کامل» هم این خط را دارد
   (`شبکهٔ سایت`). اگر خواستی دستی هم تأیید کنی:
   ```bash
   curl -sS -o /dev/null -m 15 -w 'site=%{http_code} t=%{time_total}\n' https://tisacase.com/wp-json/
   curl -sS -o /dev/null -m 15 -w 'fence=%{http_code} t=%{time_total}\n' \
     "https://tisacase.com/wp-json/wc/v3/tisa-health?consumer_key=CK&consumer_secret=CS"
   ```
   * هر دو گیر کردند (`000`/تا ۱۵ ثانیه) → **هاست**: CPU/RAM و سقف «entry processes»
     (لایت‌اسپید/CloudLinux)، استخر PHP-FPM، یا فایروالی که IP ربات را بسته. از
     `wp-admin` هم نمی‌توانی وارد شوی؟ همان لحظه سایت زیر بار است.
   * اولی `200/404` و دومی گیر → **فایروال/ModSecurity** کوئری‌استرینگِ دارای
     `consumer_secret` را نگه می‌دارد؛ قاعدهٔ «consumer» را بردار.
   * دومی `404 rest_no_route` → افزونهٔ تیسا نصب/فعال نیست (یا نسخهٔ زیر ۰.۸ است):
     `python scripts/build_plugin_zip.py` و آپلود در `wp-admin`.
   * دومی `500` با «locks are held»/`information_schema` → یک بک‌اپ یا `OPTIMIZE TABLE`
     روی دیتابیس دارد پیش‌آزمون را خوابانده؛ افزونهٔ ۰.۸.۱ این را با `lock_wait_timeout=2`
     و کشِ پنج‌دقیقه‌ای بی‌خطر کرده است.
   **تا رفعِ قطعی فروشنده هیچ کاری نکند:** بسته در `outbox` است و کارتِ خودش می‌گوید
   «🕐 سایت پاسخ نمی‌دهد» (نه ❌، نه «دوباره بزن»). وقتی علت «پاسخِ نبودن» است — نه `500`ِ
   خودِ سایت — صف هر ۳۰ دقیقه می‌کوبد و آن را **تلاش نمی‌شمارد**، پس هشت تلاشِ
   وعده‌داده‌شده برای بعد از بالا آمدنِ هاست می‌ماند (سقف ۲۴ ساعت برقرار است).
   `📤 صف من` / `/queue` همان وضعیت را نشان می‌دهد، «⟳ همین حالا» تلاش را جلو
   می‌اندازد و «🗑» ردیف را از صف بیرون می‌کند. نیم‌نوشته‌ای در کار نیست: تا
   `tisa-health` جواب ندهد هیچ نوشتنی شروع نشده، و اگر وسطِ نوشتن قطع شد همان
   `batch_id` ادامه می‌دهد نه کپیِ دوم.
2. **🟡/🔴 رسانهٔ وردپرس** → مسیرِ آپلود تصویر جدا از REST ووکامرس است (Application
   Password). بدون آن، محصول با تصویر منتشر نمی‌شود و ربات می‌گوید کدام عکس نرسیده.
3. **🕐 «به صفِ تلاشِ دوباره رفت»** → طبیعی است، فقط برای خطاهای **موقت** (`408/425/429/500/502/503/504`
   و قطعِ شبکه). **از تلگرام:** «📤 صف من» روی همان کارت، یا `/queue` — چندمین تلاش است،
   بعدی کِی، و دو دکمه: «⟳ همین حالا» (تلاش را جلو می‌اندازد) و «🗑 از صف بردار».
   یک قلمِ دیگرِ همان کاربر هم روی همین صفحه دیده می‌شود؛ قلمِ کسی دیگر نه. اگر خواستی
   دستی هم ببینی:
   ```bash
   python main.py --check-config        # خط outbox : … (N در صف)
   sqlite3 data/outbox.sqlite3 \
     "SELECT batch_id, status, attempts, CAST(next_at - strftime('%s','now') AS INT) AS wait_s, last_error
      FROM outbox WHERE status='pending' ORDER BY next_at;"
   ```
   تلاش‌ها با JobQueue هر ۶۰ ثانیه بررسی می‌شوند (و یک بار در استارت). ری‌استارت = همان
   «همین الان یک پاس دیگر». بی‌فعالیتِ چت هم صف را لغو نمی‌کند: تایمر ۹۰۰ ثانیه‌ای
   پیش از اینکه چیزی را «رهاشده» اعلام کند از `outbox.is_queued` می‌پرسد و اگر قلم
   زنده بود، کارت را با 🕐 می‌بندد (نه ⌛) و شمارندهٔ `flow_abandoned` را تکان نمی‌دهد.
   اگر خواستی یک قلم را رها کنی:   ```bash
   sqlite3 data/outbox.sqlite3 "DELETE FROM outbox WHERE batch_id='719e372625cf';"
   ```
   پس از ۸ تلاش **یا** ۲۴ ساعت، قلم `status='dropped'` می‌شود و همان‌جا می‌ماند — عمداً
   پاک نمی‌شود تا ببینی چه چیزی منتشر نشده. فایل `product.zip` آن را دستی هم می‌شود وارد
   کرد (افزونهٔ سایت) یا دوباره از ربات فرستاد.
4. **❌ «بعد از همهٔ تلاش‌ها رها شد» بدون علتِ خوانا** → علت در همان لحظه در لاگ است:
   ```bash
   grep -n "outbox\|release\|POST products" logs/bot.log | tail -40
   ```
   و اگر می‌خواهی دقیق‌تر ببینی، `VERBOSE_LOG=yes` + «🧾 آخرین محصولات» (کارتِ محصول
   خطا و هشدارها را دارد).
5. **`400` هرگز وارد صف نمی‌شود** — فردا هم همان جواب را می‌دهد؛ یعنی داده غلط است
   (قیمت، واریژن تکراری، SKU گرفته‌شده). کارت محصول همان را می‌نویسد؛ اصلاح کن و دوباره
   بفرست.

## ۶) تمرین پیش از انتشار واقعی

```bash
grep -n TISA_DRY_RUN .env            # باید no باشد تا انتشار واقعی انجام شود
```

`TISA_DRY_RUN=yes` کل مسیر را **دقیقاً** می‌راند (payload، انتخاب SKU از high-water محلی
یا مسیر افزونه/کاتالوگ، دسته‌ها، آپلود مدیا و بچ واریژن‌ها) ولی ترنسپورت جعلی است:
هیچ‌چیز روی سایت نوشته نمی‌شود. گزارش درخواست‌های dry-run فقط به `LOG_CHAT_ID` می‌رود و
صریحاً می‌گوید چیزی به سایت ارسال نشده؛ کارتِ محصول و «🧾 آخرین محصولات» آن را با 🧪
علامت می‌زنند و `product_id` ذخیره نمی‌شود، و **شمارنده‌های
فروشگاهی زیاد نمی‌شوند** ( عددِ «دیشب چند محصول شد» فقط واقعی است). «📊 وضعیت» همیشه
می‌گوید الان در کدام حالتی — قبل از تمرین یک نگاه به آن بنداز، و بعد از تمرین
`TISA_DRY_RUN` را خاموش کن و ری‌استارت بزن.

## ۷) شروع از صفر (و چیزی که با هر فایل از دست می‌رود)

ربات را متوقف کن، بعد:

| فایل | اگر پاکش کنی |
|---|---|
| `data/roles.json` | همهٔ ادمینها می‌روند؛ فقط سودو (از `.env`) می‌ماند. دوباره با `/start <کد دعوت>` اضافهشان کن |
| `data/recent_products.json` | دفترِ «این محتوا قبلاً منتشر شد» می‌رود ⇒ idempotency برای محصول‌های قدیمی سست می‌شود |
| `data/sku_state.json` | بی‌ضرر؛ از کاتالوگ اسکن می‌کند (فایلِ TTL = ۶۰۰ ثانیه است) |
| `data/learned.json` | قاعده‌هایی که خودت تأیید کردی می‌روند؛ اصلاح‌های تأییدنشده (`pending`) هم با آن‌ها می‌روند |
| `data/preferences.json` | دکمه‌هایی که برای ادمینها روشن کرده بودی به پیش‌فرض برمی‌گردد |
| `data/tracking_ledger.json` | فقط هشدار «این فایل قبلاً پردازش شده» کم می‌شود |
| `data/outbox.sqlite3` + `outbox_files/` | تلاشِ دوباره‌های باز گم می‌شوند — **اول `--check-config` را ببین**، اگر N در صف است، این کار را نکن |
| `data/metrics.sqlite3` | شمارنده‌ها به صفر برمی‌گردند («📊 وضعیت» می‌گوید «هنوز چیزی ثبت نشده»، نه «همه‌چیز سالم بوده») |
| `data/flow_state.json` | نشانهٔ جریان‌های نیمه‌کاره می‌رود؛ اگر چیزی واقعاً نیمه است، خود کاربر باید دوباره شروع کند |

```bash
supervisorctl stop tisabot           # یا systemctl stop tisaposttowp
cp -a data "data.bak-$(date +%F-%H%M)"    # بکاپ همیشه، حتی وقتی «مطمئنی» لازم نیست
rm data/sku_state.json data/tracking_ledger.json
supervisorctl start tisabot
```

**بکاپ‌گیری منظم** (همه‌چیز در یک دایرکتوری است، به شرطی که `TISA_DATA_DIR` را بیرون
از کد برده باشی — «📊 وضعیت» اگر داخل کد باشد هشدار می‌دهد):

```bash
tar czf /var/backups/tisaposttowp-$(date +%F).tgz -C /var/lib/tisaposttowp .
# بازگردانی: سرویس را متوقف کن، بازگردانی کن، سرویس را روشن کن
```
